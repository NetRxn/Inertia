# Member contribution candidate boundary

## What is implemented

The additive `src/contributions` library prepares a bounded, server-curated public task input and stages inert, untrusted evidence. It does not register a tool, HTTP endpoint, scheduler, sandbox, credential, enrollment, deployment or issue-completion writer. Nothing is enabled by the current worker or manifest. Integrators must explicitly provide an enabled gate; disabled calls return before any source/native/receipt access.

An authenticated transport supplies the member/agent identity and a non-reusable authority epoch for the exact current holder/execution attempt, independently of submitted fields. The server must issue a fresh epoch on handover, restart or reconstruction, even when a provider lease/generation resumes X→Y→X. It must not derive this epoch from a reusable generation, successful sync or stop receipt. A stale authenticated epoch is rejected before native reads. A trusted enrollment source supplies the exact company/project/issue/task revision, native run and checkout, opaque provider lease/current lifecycle generation and disposition, enrollment revision/expiry and approved data/artifact classes. Only `active` lifecycle evidence is admissible. Unknown/unreachable, lost, fenced or superseded is not proof of termination or authority. Generation must match exactly; successful artifact transport is not proof of generation ownership. Enrollment/source freshness and current provider evidence are the source adapter's responsibility.

The concrete native adapter uses pinned `PluginContext.issues.get(issueId, companyId)`, `agents.get(agentId, companyId)` and `issues.summaries.getOrchestration({issueId,companyId,includeSubtree:false})`. Configured scope is checked before native reads. Only a projection is returned internally; raw titles, descriptions, company-wide records, other tasks and credentials are never exported. Only server-curated `input` is sent to a member. Native issue revision hashes conservatively include updatedAt and relevant content/ownership. A current running run must belong to the exact issue and agent, with matching checkout and execution run. This adapter does not acquire work or call `assertCheckoutOwner`, which can adopt stale checkouts.

Artifacts are inline UTF-8 `.txt`/`text/plain` or `.json`/`application/json`, at most 8 unique safe names, 64 KiB each and 128 KiB total. Exact declared SHA-256 is checked. Extra fields, URLs as retrieval instructions, path traversal, executable/archive types, shebang/HTML/binary signatures, invalid UTF-8/control bytes and invalid JSON are rejected. Text remains untrusted even when valid: a script described inside prose is still possible, so consumers must never execute it or render it as active HTML. There is no URL fetch, filesystem write, archive extraction or process execution.

## Correlation and review semantics

`createContributionJournal` uses the existing native plugin `bridge_runtime` receipt storage in `inertia:member-candidate:v1`, not a separate task ledger or database. Immutable insert-if-absent is keyed by the hash of the complete binding. Canonical artifact ordering and content hashes make identical retries converge; changed payload for the same binding conflicts. A lost insert response is reconciled by the immutable identity before returning. Unknown storage outcome returns `uncertain`, never success.

`candidate-for-review` means only that the exact untrusted candidate is durably staged, not that a human saw it, native review was dispatched, or the result was accepted. Current authorization is checked again before returning the receipt. A revocation racing staging can leave an inert receipt, but never a completion; review must reauthorize before displaying it. Do not give members raw journal or plugin database access. An operation ID is correlation, not a bearer capability. No member artifact retrieval API is provided.

## What remains before activation

- Authenticated ingress that derives identity server-side, rejects unrecognized request fields, enforces a bounded body before parsing, and passes no company-wide native client to members.
- Production enrollment/membership authority with explicitly approved scopes and current revision/expiry. Repository-admin access is not DAO enrollment. NTF11 still requires a participant and enrollment administrator.
- Current lifecycle evidence from the operator-selected native environment/provider, with exact opaque holder/lease/generation, native run/checkout binding and fail-closed unknown state. Existing native environment/provider hooks should be reused, not replaced or copied into Inertia.
- Qualified actual sandbox, isolated workspace, permitted filesystem/network/process behavior, cancellation/timeout/connection-loss and cross-member denial. No provider or model execution ran in this slice.
- Atomic input release/revocation coordination if production policy requires linearizable revocation of exports; sequential reads here do not establish that property.
- Native review handoff/display and final acceptance in an owning native transaction or qualified equivalent. Atomically fence current membership, enrollment, task revision, run/checkout, lifecycle and artifact policy; record one authoritative completion per task revision and immutable operation identity. Generic privileged `issue.update` after a check is not that primitive. Reconcile uncertain acceptance before retry. Final task completion and human review remain native.
- R-C05 native follow-up creation with parent context, reason, acceptance criteria, deduplication and budget/depth/rate bounds is a later slice.

## Reproduction and evidence limits

Run `npm test`, `npm run typecheck`, `npm run build`, then the existing `node scripts/cloud-rehearsal/run.mjs` after its documented pinned host/PostgreSQL prerequisites. The harness owns a disposable local database and refuses external database overrides. It now derives job inventory from the actual manifest rather than a stale fixed count.

`check-member-boundary.mjs` exercises two synthetic native members/agents/tasks, native checkout, exact native projections, actual plugin PostgreSQL receipts, concurrent identical submits, changed-result conflict, committed-but-lost insert response, guessed task/company receipt denial, hostile artifacts, current native membership revocation and native stale-checkout adoption followed by rejection of the obsolete result. It leaves both tasks in native in-progress state. The existing native-member fixture separately checks competing claims, wrong holders and terminal recovery. These are actual pinned native-service tests, not full HTTP authentication, live member enrollment, provider execution, native human review or atomic authoritative acceptance. The second-member demonstration remains open.
