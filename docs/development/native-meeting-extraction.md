# Native meeting extraction and local preproduction

This is an additive completion of R-M01–04 and R-I01–04. It uses existing native issues, wakeups, checkouts, objective mappings, private runtime state and the website v1.1 publisher. It does not create a second coordinator, grant task authority from transcript text, use a direct provider SDK, or modify the externally owned website API.

## Configured native work

Each `roundtable.meetings[]` entry may configure `nativeExtraction: {projectId, issueId, agentId}`. The issue must already exist in that project and be assigned to the configured agent, with status todo, in_progress or blocked. The manual source reconciliation persists a source-bound extraction request before waking that issue. The reason contains only a configured meeting reference, never transcript content. A lost wake acknowledgement is not success; retries use the same native idempotency key.

`meeting_source_context({meetingId})` (or the opaque `{meetingRef}` pointer supplied on native follow-up work) resolves the configured source only for its actual authenticated active native task. `submit_meeting_candidates({meetingId, requestHash, notes})` validates and persists the exact result, then resumes the already-admitted publication. The model cannot select paths, origins, company, agent, run, principal, permissions or source versions. The common `assertNativeTaskRun` helper authenticates the exact running native run and active assignee before checkout (which can adopt ownership), rechecks them after checkout, and rechecks configuration on both sides.

Private runtime state contains the current raw source and staged/accepted candidate output. A result is reusable only after a separate durable accepted marker; failed post-stage authorization never promotes staged notes. An uncertain acceptance write returns pending and is reconciled by exact request identity. Source is rechecked after the final checkout, followed by read-only task/config validation, before protected context is returned. Native issues/documents receive no raw content. The context response returns `sourceEvidence: owner-file | drive`, original identity/revision/audience, sourceHash, requestHash and a data-not-authority instruction. Native tool responses/run logs may persist private content in the configured native host. Its access and retention must be admitted before using real protected inputs; being company-visible is not a substitute for member source permissions.

## Useful output and honest limits

The unchanged v1.1 extractive-v1 contract permits complete unchanged source lines with 1-based evidence only. It does not permit faithful paraphrase, sub-line evidence spans, rewritten/cleaned sentences, invented owners or dates. The full transcript is preserved separately, with only existing newline/outer-whitespace normalization. Native instructions request concise substantive excerpts, omit filler, distinguish explicit resolved choices (including defer/reject) from tentative discussion, and retain uncertainty. Tentative discussion belongs in notes, not the decision section. Actions require an actual request/commitment; owners remain null. Limits are 12 notes, 20 decisions, 30 actions. These categories are unverified candidates, not adopted decisions, formal votes or executable instructions.

Code proves exact evidence, identity, limits and authority boundaries. Synthetic tests cannot prove that a real model chooses useful lines or correctly understands every ambiguous utterance. Actual generated output must still be qualified. Long filler-heavy source lines cannot safely be paraphrased under v1.1; see the separate proposed v1.2 contract rather than claiming cleaned summaries exist.

If no native extraction binding is configured, the source stays pending with `native_extraction_binding_required`; no empty-candidate publication is sent or called complete. Adding the binding later resumes the same source revision. While extraction runs, status is `extraction_pending`. No new source revision is fabricated. Source changes during extraction invalidate the request; source is reread before publication bytes are admitted. Once bytes were sent with an uncertain outcome, the existing exact-byte readback/recovery contract remains authoritative.

## Meeting-derived triage

Existing `roundtable.nativeIntake` still creates/reconciles one reference-only follow-up in the native backlog. To authorize that assigned intake agent to resolve protected meeting evidence, additionally configure `projectId` and `sourceAccess: true`; the new issue receives that project. Reference-only issue creation by itself does not grant source access. The context tool verifies the exact durable objective mapping, current revision marker, current issue and actual active assigned run, and suppresses withdrawn/stale/reassigned mappings. The issue contains an opaque meetingRef tool pointer, so no external meeting ID knowledge is required. Optional `allowedAgentIds` explicitly admits additional reader agents only on current verified native descendants of that exact follow-up and project. New hires are never automatically admitted. Readers can read candidates for normal native decomposition/triage, but cannot replace the extraction result. The coordinator continues to own child tasks, review, priorities, budgets and the coherent final result. Candidate actions never authorize purchases, outreach or an adopted motion.

## Local input and publication

For source work without Drive credentials, an entry may set `ownerFile` to an administrator-pinned absolute owner-only JSON file. The envelope is the existing internal Source shape: meetingId, sourceId, revision, ready, kind, audience, text. Its sourceId must match the configured imported `drive:<fileId>` provenance, revision must be a positive decimal, audience members, kind transcript and ready true. This is a trusted owner export with explicit provenance, not a claimed live Google read. The reader rejects symlinks, other-owner/group/world-readable files, oversized/unstable content, invalid UTF-8/JSON and foreign identity. It reuses the objective owner-file reader. Production volumes, file ownership, retention and agent mount isolation remain deployment obligations.

Set `roundtable.publicationMode: local` for private SQL publication/readback. This uses the unchanged website publisher against a local adapter, persists exact current/previous envelopes and receipts together, enforces CAS, and reconciles restart/replay. It resolves no website credential and uses no HTTP network. Results explicitly include `publicationMode: local`, with `local-` publication IDs. The members audience value exercises the wire contract; it is not proof of an external member portal or deployed membership authorization. Local readback remains internal to the protected plugin database. Local reads and writes recheck current admission, including the absence-read-to-write boundary. Publication mode is part of durable lifecycle identity; switching an existing local binding to website fails closed instead of relabeling local evidence or rebasing against a nonexistent live head. There is no implicit migration. The existing website mode still requires its scoped credential/admission and current server contract.

Local source and local publication are independent: omit sourceTokenRef when all meetings have owner files, and omit websiteTokenRef only in local mode. Neither mode enables a recurring schedule. Gemini-only input remains summary-only with transcript_required; no content is substituted for a transcript and no notes-only website success is claimed.

## Verification and operational boundary

SDK harness tests plus actual PGlite SQL exercise native tool registration, private state, owner-file inputs, post-checkout/source races, candidate validation, protected follow-up reads, exact local receipts, same-revision delayed binding, correction and restart. Existing real source/publisher adapters remain tested with controlled HTTP. These are source/synthetic qualification, not a running native host, actual model quality, live Drive, website, membership, Buzz or deployment evidence. Live permissions, source ownership, native tool/run-log audiences, retention, configured issue/agent mapping, connector admission and stopped-worker recovery must be qualified separately.
