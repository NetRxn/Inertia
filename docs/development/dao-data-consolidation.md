# DAO data consolidation contract

Storage and activation contract, 2026-10-24. Domain/graph and objective-intake migrations are merged and disposable cloud qualification passed. Durable native capture and DFW acceptance are implemented and independently reviewed; production source/transport, retention/archive, writer-fence composition and cutover remain pending.

## Storage and authority

- **DAO relational database:** reuse one database on the existing managed PostgreSQL service for funding and meeting information. Default to isolated domain schemas and least-privilege roles, subject to U14 provider qualification. A service, schema, database, managed instance/cluster and physical server are different boundaries; this design does not require a separate server per backend or assert shared physical placement.
- **Paperclip database:** independent native persistence for tasks, authenticated decisions and plugin transport records. Funding-domain review audit references those decisions; reconciliation is not a cross-database atomic transaction.
- **Helix:** core derived indexed graph of partner organizations, relevant people/roles, activities, contributions and relationship owners. DAO PostgreSQL owns admitted evidence, typed facts/history and the transactional projection outbox; Helix is rebuildable. Preserve canonical IDs, source revisions/hashes, scope and delivery stage. Broader 990 enrichment and optional vector/semantic retrieval follow later. Native human decisions and packet-bound DAO governance retain their respective authority.

Funding services own evidence, proposals, immutable packets and domain review validation. Meeting/website services own publication versions, organizational knowledge access and membership enforcement. Shared storage does not allow unrestricted joins or direct cross-domain mutation. Prefer authorized service reads; any justified cross-schema view gets narrowly scoped grants. Member agents receive task-scoped tools, never shared database credentials. Existing protected artifact storage retains exact bytes; relational references/hashes do not require moving binaries into PostgreSQL.

The DFW knowledge service extends Task 6 within its existing Alembic-owned schema; website/member/project and meeting records retain their Drizzle owner and canonical IDs. `OrganizationKnowledge.organization_id` identifies the owning DAO/applicant access boundary; the typed assertion carries the subject partner identity. Trusted service adapters expose only needed fields.

A research commit writes permitted evidence, typed assertions, audit history and outbox rows atomically in DAO PG. Helix projection uses stable keys, monotonic revisions, atomic target-side fencing and readback reconciliation; acknowledge PG delivery only after durable application. Backfill/rebuild preserves a gap-safe sequence and propagates tombstones. Delivery is at least once, with idempotent convergence and separate acknowledgment in each store.

Helix queries enforce tenant/audience/project/opportunity scope at every hop and revalidate current source/access/version in PG before hydrating any result. Revocation denies access immediately while removals propagate. During graph outage/lag, bounded indexed PG selection returns explicitly degraded coverage; unavailable authoritative checks withhold affected results. The operational graph remains a release requirement. See [core requirements](../../spec.md) and [T-K01–12](../../testing.md#operational-partner-graph-acceptance-live-qualification-pending).

One migration owner per object: Drizzle for DAO website/meeting tables; Alembic for funding schema and its own history table. Keep existing histories, scope both tools, and review generated SQL for cross-domain changes. Do not let both ORMs recreate or adopt the same tables. The platform operator owns schema/role/extension provisioning; runtime roles cannot perform DDL. Existing website tables may remain in their current schema during staged adoption, with explicit grants and ownership, rather than forcing a risky cosmetic move. Confirm schema/role support first; if it cannot meet isolation or PostGIS needs, report the specific incompatibility before selecting another database, not a silent new server.

## Gated migration plan

1. **Read-only inventory (U14):** record deployed PostgreSQL version, provider capabilities, actual funding/meeting stores, tables, migration heads, sizes, identifiers, collisions, extensions, current readers/writers and audience constraints. Include any Meeting Mode records and distinguish source from publication data. Do not assume every repository is deployed or holds unique data.
2. **Backups and ownership:** establish recoverable source/target backups and test restore in isolation. Agree schema/table ownership, scoped migration histories, connection/search-path settings and runtime/migration roles. Preserve existing object and artifact IDs; map collisions explicitly, never title-match or silently merge records.
3. **Isolated qualification:** run existing Drizzle/Alembic migrations against an isolated representative copy, scoped to owned objects. Check PostgreSQL/PostGIS types, JSON, date/time handling, constraints, sequence/ID behavior, raw SQL and concurrent domain reads/writes. Prove cross-schema and row/audience denial, including future-table default grants. Use existing tools, not a new migration engine.
4. **Backfill and reconcile:** stage a repeatable transfer preserving source IDs, foreign keys, provenance, content hashes, packet/publication versions and review audit. Compare counts and identity/hash-level samples plus every immutable packet/review linkage; resolve discrepancies before cutover. Keep originals and rollback mappings.
5. **Authorized cutover:** pause affected writers, capture/reconcile the final delta, switch only scoped service bindings, then verify consistent packet reads and meeting publication/readback. Resume one authoritative writer per domain. Paperclip stays independent; reconcile native decision references and pending external effects rather than replaying them blindly.
6. **Rollback:** define restore point and reversal criteria before cutover. If checks fail, pause writers, retain/reconcile post-cutover writes, restore the compatible database/schema and application configuration together, and verify IDs/hashes/audiences before resuming. A URL flip or binary downgrade alone is not recovery. Do not remove old stores until reconciled retention and recovery gates are met.

Acceptance is T-D01–06 in [testing.md](../../testing.md#shared-dao-storage-acceptance-planned). This document adds no migration code or claim of deployed compatibility. Private contents, database URLs and credentials stay out of public artifacts and fixtures.
