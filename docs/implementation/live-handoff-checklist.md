# Connected rehearsal and live handoffs

Run `npm run demo:workflow` from a development checkout (Node >=24.11, `npm ci`). It builds once, prints the journey, and writes one deterministic receipt to `runs/workflow-receipt.json`. The ignored `runs` directory is local output. The runtime package excludes the rehearsal and its PGlite dependency.

The rehearsal uses the actual Roundtable validation/hash core, Postgres bridge migrations and durable inbox/outbox, Paperclip adapter, signed Buzz transport, and grant snapshot/governance evaluation. External I/O is synthetic. Each fresh run produces the same manifest; within the run a reconstructed bridge replays the signed reply without a second native mutation.

The fixture orchestrator seeds one initiative/issue from an unverified action candidate and attaches the meeting output hash/revision and frozen packet ID/version/hash. That seeding is the integration seam to replace with native Paperclip work creation. The ordinary paired acknowledgment references the exact packet, but the separate governance evaluator supplies the grant authority receipt. Publication stays pending on unknown readback. No live service is contacted.

Cloud is the default development and verification environment. Laptop Docker checks are optional, used only for a specific cloud blocker or platform check; they do not gate this rehearsal.

## Cloud deployment profile

**Status: proposed.** one always-on Paperclip application instance in an ordinary cloud container/VM, one independent durable Paperclip PostgreSQL database, and the existing Buzz service. Funding and meeting records reuse the existing DAO relational database under isolated domain schemas/roles; this does not provision another domain database per service. Keep `netrxn.inertia` inside Paperclip's admitted plugin runtime. Use the host's native company, CEO/hiring, issue, assignment, wake, review and audit primitives. Keep scheduling, tasks, identity and execution ownership native. The plugin SQL namespace stores delivery/correlation records only.

Initial sizing hypothesis: 2 vCPU/4 GiB, matching the [synthetic Docker check](../qualification/docker-http-receipt.json). Production capacity testing is pending. Prefer an existing managed PostgreSQL service with automatic backups; otherwise budget and operate a durable database separately. Keep production data, plugin state, host configuration and any required host secret/encryption material on persistent storage or the provider's supported secret store. Do not rely on an ephemeral container filesystem.

- **Private by default:** authenticated, member-only Paperclip using the installed release's supported authentication and onboarding paths. Set the real canonical HTTPS origin and allowed hosts through supported host configuration. Validate proxy forwarding, session behavior and native company membership before connecting Buzz. Never expose the qualification fixture's `local_trusted` mode or trust-authenticated database to a shared/public network. A reverse proxy is not a substitute for native authorization.
- **Network/runtime:** one TLS ingress to Paperclip; database reachable only from the application/operations path; outbound HTTPS to the verified Buzz origin and only the approved services needed by the selected host adapters. Run non-root with no privilege escalation, no Docker socket or host-home mounts, bounded resources and writable paths limited to required runtime state. Verify the supported host actually starts under these restrictions rather than silently disabling them. The qualification fixture's `network: none` is not a live deployment profile.
- **Immutable release:** use the exact qualified official host package and reviewed Inertia package/lock, record their digests, and disable unattended version changes. Qualify the latest stable candidate before promotion; pin the running image. Reuse [the upgrade check and qualification](../qualification/paperclip-upgrades.md); do not add another upgrade script.
- **Later untrusted member-owned execution, not the Wednesday gate:** the cloud service owns orchestration, not members' personal runtimes. Before admitting that path, qualify client-side isolated sandboxes/worktrees with minimum task data and separately scoped native access. No shared signing key, database credential, host administrator credential or another member's workspace goes to an agent. Private execution-hardening integrations remain private dependencies, not source copied into this public package. Require live cross-member denial and revocation tests.

### Maintenance and stop path

Use native plugin health and the three existing jobs, not another monitoring database. Check `pendingReceipts`, `uncertainMutations`, `blockedReceipts`, `oldestPendingAgeSeconds` and successful sync freshness together with host/job availability. Disabled health is expected; a growing backlog, stale jobs or an uncertain mutation is not. A host that is down cannot report its own health, so use the deployment provider's existing uptime/backup alerts where authorized.

Follow [existing recovery guidance](../operations.md#recovery-without-babysitting): allow bounded normal retries; correct permanent access/configuration failures before “Retry blocked deliveries”; use “Backfill connected conversations” after a long offline period. Never delete inbox/outbox rows to force replay or re-sign an uncertain outgoing event. Unknown native outcomes need authoritative native readback.

To stop new bridge processing, set the company's `enabled` to false and verify readback; already in-flight work may finish, so inspect outstanding native results rather than assuming cancellation. Revoke a pairing for a specific identity through native configuration. Keep durable delivery state intact. Before any upgrade, reuse the existing upgrade gates and restore-tested backup. If migrations are incompatible or uncertain, restore the prior database/configuration and matching host/plugin together; rolling back a binary alone is unsafe. Reconcile any external Buzz events/native results after a restore before resuming so a stale backup cannot blindly replay already-applied work.
