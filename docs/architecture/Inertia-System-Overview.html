02

Three journeys, one evidence trail.

Each flow preserves source identity, scope and outcome. The complete live journeys are acceptance targets, not claims made by fixture demos.

A. A meeting becomes usable knowledge and work

Meet / Gemini → organization Drive → Inertia → member portal → native work

End-to-end live acceptance pending
1Capture ready sourceSource admission

Observe the authorized Drive folder. Record meeting, file, revision, original hash and audience.

2Ground the outputsRoundtable core

Separate cleaned transcript from notes and decisions. Preserve quotes and uncertainty, not invented owners.

3Publish + read backCaller implemented

Atomically upsert through the proposed website contract. Verify full content, version, URLs and members-only audience.

4Resolve action candidatesNative wiring

Attach source references to native issues. A trusted policy resolves assignment; ambiguous commitments stay unresolved.

5Return useful linksLive continuity

Members see the portal outputs and native work. Return supported outcomes through the bound Buzz thread.

Quality rule: A summary-only source yields notes plus a missing-transcript exception, never a fabricated transcript. Routine in-policy publication is automatic after one-time authorization, not a vote for every meeting.
Proof of successOne source revision → two correct outputs → verified member-only readback → linked native work; duplicate notifications and corrections do not multiply results.

B. A grant candidate becomes a reviewable, votable packet

Current opportunity → authorized DAO context → reviewed draft → bound vote → authorized action

Exporter + verifier pending
1Refresh the candidateReuse scanner

Read current deadline and eligibility evidence. Resolve direct versus partner route; public facts alone do not prove eligibility.

2Read DAO contextAuthorized portal access

Retrieve formation, governance and applicant evidence with document version, hash, citation and access class.

3Draft, review, freezePacket binding core

Preserve engine signoffs. Freeze packet ID/version, canonical content, attachments and review hashes together.

4Verify voted authorityVocdoni integration

Match network, proposal, final result, action and exact packet. Verify any applicable final-action stage from the actual example.

5Accept + hand offTransactional acceptance

Recheck currentness; record authority on native work. Preserve separately authorized representative submission.

Two different approvals: Native workflow review coordinates work. A verified DAO vote grants only its exact packet/action authority. A changed packet needs renewed authority; a vote is not automatic funder submission.
Proof of successA current opportunity + reviewed immutable packet + valid effective vote receipt. Wrong network, stale content, pending results or mismatched actions cannot pass.

C. A second member contributes safely

Pair member → native checkout → isolated execution → validated result → bounded follow-up

Required product slice
1Enroll a scoped agent

Verify active membership, capabilities and allowed projects. Repository-admin access is separate from DAO permissions.

2Acquire eligible work

Native assignment, dependencies and atomic checkout select one owner. Budget and policy still apply.

3Run on member hardware

Qualified execution isolation, minimal task data and bounded tools. No shared publisher or submission credentials.

4Validate the contribution

Check run identity, revision, artifact size/type and provenance. Native review accepts one authoritative completion.

5Continue with context

Create a justified follow-up with parent/goal, reason, acceptance criteria and deduplication key, within limits.

Proof of successA second member completes useful work; an unauthorized or revoked member is denied; reconnect and duplicate results do not create duplicate completion.
Y2 closes the loop.Register a relevant grant, program or partner interest. A sourced update maps to the existing issue or a deduplicated follow-up. The account/API adapter is planned and remains included in the product scope.
03

Data can travel. Authority cannot be guessed.

These boundaries let the system be useful without turning a chat reply, model output or member machine into an administrator.

↔

Conversation boundary

Bridge controls implemented
  • Signature → trusted key pairing → native membership and authorization.
  • Relay/channel/thread → configured company and issue, never caller-selected authority.
  • Human and agent attribution stay distinct. An agent reply is not a human vote.
  • Lost responses reconcile against native state before another mutation.
▣

Knowledge boundary

Website enforcement pending
  • Privy login alone is not active DAO membership.
  • Machine resource allowlist AND responsible user’s document ACL must pass.
  • Enforce access before search snippets/counts and on the actual source bytes.
  • A gated portal page cannot make publicly accessible IPFS content private. Restricted evidence stays scoped.
◇

Execution boundary

Runner qualification needed
  • Member-owned executors receive only authorized task inputs and scoped tools.
  • Trusted server validates results and controls external writes.
  • A plugin is trusted extension code, not an untrusted-code sandbox; a worktree alone is not isolation.
  • Reuse existing hardening through public contracts. PPC2 implementation remains private, not copied into public Inertia.
Sources → native work → accepted result → receiptKeep stable IDs, source revisions, content hashes, provenance and audience at every hop.

06

Six concrete gates to a credible demo.

Each gate has an owner role, a next action and observable acceptance evidence. These are existing delivery requirements, not a new approval process.

G1

Connect the operational spine

Inertia engineering + integration owner · U01/U03/U09/U10

Configure the authenticated private host, durable PostgreSQL, existing Buzz relay and trusted pairings. Select the existing CEO and assign bounded intake under native run policy.

Accept when: a real paired reply, native comment/run and signed receipt agree; delegated work IDs are recorded.
G2

Admit the members-only meeting path

DAO administrator + website owner · U04/U05

Confirm ready Drive outputs; roll out the proposed website contract with active membership, document/source ACLs and atomic publication/readback. Wire one native job owner.

Accept when: transcript + notes read back correctly to the allowed audience; duplicate and correction cases converge.
G3

Bind the actual governance route

Grant owner + governance owner + integration · U06/U11

Refresh the candidate, retrieve authorized DAO evidence, complete the production exporter, and use the user’s Vocdoni example to establish all effective final stages.

Accept when: a current reviewed packet’s exact hash/action matches a verified final result; native acceptance is transactional.
G4

Qualify the second member

User + engineering qualification · U02/U08

Separate repository-admin access from DAO-agent enrollment. Qualify existing hardening through native execution contracts and scope task inputs and tools.

Accept when: useful contribution succeeds; cross-member access, revoked identity and hostile/stale artifacts are denied.
G5

Connect Y2 interests and updates

Y2 teammate + integration · U07

Confirm account/API access, visibility and stable update identities. Implement registration and update mapping to the existing native initiative.

Accept when: a relevant sourced update creates or updates the correct work once, including replay.
G6

Rehearse and hand off the proof

User + engineering + participants · U12

Confirm named owners and logistics. Run all three live journeys with recovery and audience checks, then assemble reproducible receipts and the owner’s submission package.

Accept when: all three outcomes are demonstrated and the remaining gaps, if any, are explicit.
