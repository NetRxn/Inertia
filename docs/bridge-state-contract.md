## Authority and supported decisions

Bindings and pairings are administrator-owned configuration. Reload them before acting. Native company/issue/user IDs come from these records, not signed message text. Signing establishes key ownership; native policy establishes membership. Unknown, revoked, agent-kind and ambiguous pairings are rejected. Native host membership checks remain the final authority for writes, including replay of an already-resolved decision.

The initial command set is ordinary comments plus exact `/inertia accept <card-token>` and `/inertia reject <card-token>`. Tokens are opaque random values generated by the connecting service, persisted once with immutable company/issue/interaction/digest mapping. Unknown commands produce instructions, not comments.

Direct responses support plain `request_confirmation` cards only. Target-bound, tool-action, secret-proposal and other interaction kinds use the richer native UI. The pinned host replaces plain confirmation drafts by creating new IDs and expiring older siblings. The adapter rereads and checks the exact content digest before resolving; native atomic resolution owns dashboard-vs-Buzz races. A changed pending card is rejected. SDK upgrade requires rechecking this immutability contract because the SDK does not offer a digest compare-and-set argument.

## Crash safety

Inbox uniqueness is `(relay,eventId)`. Receipt keys must also include the relay. Atomic insert chooses one claimant; no timeout or lease grants another attempt. Applying or uncertain comments are reconciled, never blindly created again. Terminal outcomes cannot be replaced.

Comments carry `sourceMarker(binding,eventId)`. Reconciliation must require the exact expected body and paired `authorUserId`, not a marker substring alone. Authenticate through trusted pairing; use the marker only for correlation.

Save the native outcome before creating its outbox record. Recovery returns final rows missing an outbox record and unresolved applying/uncertain rows. The deterministic receipt key creates at most one persisted signed event. Publication retry must use that exact event. The store treats serialized event bytes as transport data; the connecting service validates/signs events before insertion.

Host I/O errors do not expose database SQL, parameter values, credentials or source bodies through the store boundary. The service maps the safe error to an operator status. Database failures may have uncertain outcomes; do not assume a failed call rolled back.

## Fair recovery and relay retry advice

Migration `003_delivery_recovery.sql` adds durable recovery scan timestamps and outbox retry eligibility. `listRecoverable` rotates a bounded batch by last scan time, marking only the selected `(relay,eventId)` identities in one parameterized update. A permanently uncertain first batch therefore cannot starve later uncertainty checks or completed actions needing receipts, including after reconstructing the store. A scan touch never changes lifecycle state or authorizes another native mutation. Concurrent scans can repeat safe reconciliation, but never reclaim a comment action.

`markDeferred(receiptKey,retryAfterMs)` preserves relay retry advice in PostgreSQL. Eligible delivery excludes future `next_attempt_at`; a later shorter delay cannot reduce an existing deadline. `listOutbox(limit,after)` supports stable keyset pagination for delivery scans. Preserve its raw `createdAt` timestamp string and `receiptKey` in the cursor rather than rounding through a JavaScript Date. The caller advances across pages and resets at the end, so filtered foreign records cannot permanently hide later eligible work.

Regression tests first reproduced starvation behind 102 unresolved records, missing retry persistence and repeated first-page delivery. Tests then passed against actual PGlite SQL. All four new/changed SQL execution paths and four additive migration statements passed the exact pinned host validators.
