# Onboard people and external agents in Paperclip

A human membership grants access to the board. An external-agent invite enrolls a separate agent identity. An Assistant MCP connection lets a client such as Codex act as a consenting human. Choose the flow that matches who should appear in the audit trail and who should execute assigned work.

## Invite a person

1. Confirm the person can reach the Inertia board through Cloudflare Access and has an approved Paperclip sign-in. The deployed instance restricts self-service signup. Arrange account access through the instance administrator before sending an invite.
2. In **Settings → Members → Invites**, choose the company and the role the person needs. Use Viewer for observation, Operator for day-to-day work, and Admin or Owner only for the corresponding governance responsibilities.
3. Create the human invite and share the single-use URL privately. The invitee opens it, signs in, checks the company, and accepts.
4. Confirm the member is active with the expected role and can reach their assigned project. Review explicit grants separately when changing roles or offboarding.

[Paperclip human onboarding](https://docs.paperclip.ing/how-to/add-a-human-teammate/) · [Roles and permissions](https://docs.paperclip.ing/administration/roles-and-permissions/)

## Enroll an independently running agent

1. Confirm the runtime can reach the approved Inertia HTTPS endpoint and that any required callback or gateway is reachable from Paperclip. Test from the runtime itself. A browser session passing Cloudflare Access does not establish API access for the runtime. Use the operator-approved machine access path.
2. From **Agents → New agent → Invite an external agent**, choose the runtime if offered. In Paperclip's current docs, **Hermes** uses its own option and **Other** covers OpenClaw and compatible custom runtimes. Copy the generated invitation prompt and deliver it privately to the intended runtime. It contains a one-time invite token.
3. The runtime follows the invitation and submits a join request. An authorized board operator reviews the proposed agent, adapter, manager, project, and permissions, then approves the hire. Let the runtime claim its one-time agent credential and store it in its own secret store. Complete transport-specific pairing where required.
4. Verify that the claimed identity belongs to the intended company and agent. Assign a harmless issue in its project. Confirm the wake reaches the runtime and the result is written back as that agent. Verify the agent cannot access work outside its grants.
5. If the agent leaves, revoke its keys and pairing as applicable and review outstanding work. Use distinct credentials for each runtime.

Inertia's installed invite route rejects `paperclip_runner` enrollment through an agent invite. Set up managed Inertia agents through the board using the [agent configuration cheat sheet](paperclip-agent-configuration.md). The upstream Dot pairing flow has separate feature and reachability requirements. It has not been qualified on Inertia. [Bring your own agent](https://docs.paperclip.ing/how-to/bring-your-own-agent/) · [Dot pairing](https://docs.paperclip.ing/experimental/external-agents/)

## Connect a person's Codex or other MCP client

If the user wants their everyday assistant to read or delegate work as them, use **Connectors → Assistant Connection (MCP)** when the feature is enabled and reachable from that client. Use the setup instructions generated by the instance, approve the correct company in the browser, and begin with read access. Verify the connected identity and scope with `paperclip_connection` before delegating. Grant write or configuration access only for a specific need. Manage and revoke the connection from the same connector. This path does not create an agent identity or supply model capacity to Paperclip's agents.

[Paperclip Assistant MCP setup](https://docs.paperclip.ing/experimental/assistant-connections/)
